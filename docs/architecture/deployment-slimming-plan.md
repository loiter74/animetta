## 1. 深层需求：让核心能力的成本有边界

“依赖多、部署麻烦、想压缩”背后，主要是以下需求。右栏是对用户诉求的分析判断，具体实现证据见下一节。

| 表面体验 | 更深层的需求 |
| --- | --- |
| 换台机器要准备很多环境 | 主应用可迁移，机器只需具备明确、少量的前提；模型环境独立准备 |
| 启动前检查链长，不清楚卡在哪里 | 启动按所需能力执行，失败定位到一个组件，核心可用与功能就绪分别表达 |
| 没用某个功能，也受它的依赖影响 | 关闭能力后，安装、导入、初始化、预检、资源加载都不再承担该能力的成本 |
| 改界面或业务代码影响模型服务 | 应用与模型分别更新、重启，GPU 模型不随普通应用部署重新加载 |
| 神经网络环境冲突、维护成本高 | 必要模型拥有独立环境和锁；简单功能可使用明确的规则或现有远端能力 |
| 想把重要能力做成通用服务 | 模型服务只接收任务并返回结果，可以被其他应用复用；角色、记忆和直播规则留在 Animetta |
| 功能越来越多，整体越来越难控制 | 新功能增加自身成本，核心启动和安装的成本保持稳定 |

因此，压缩目标应同时覆盖**用户操作步骤、默认依赖、启动依赖链、运行资源和升级影响范围**。仅减少直接依赖数量，或把代码移动到几个新目录，无法保证这些成本下降。

## 3. 目标架构：轻量主应用、可选模块、独立推理服务

建议保留一个具有清晰模块边界的主应用，按环境、资源和更新周期隔离推理服务。

| 边界 | 默认包含什么 | 负责什么 |
| --- | --- | --- |
| Animetta 主应用 | 对话与人格、LangGraph、Live2D 舞台及后台、记忆 v2、HTTP Provider 客户端、认证与基本观测 | 拥有角色与业务状态；处理输入、召回、回复、表演和权限 |
| Redis | 继续作为一个基础服务 | 登录会话、持久检查点；维持当前正确性契约 |
| Qwen TTS 宿主服务 | 保留现有 Windows 服务 `127.0.0.1:8767`，独立安装和长期复用 | 声音模型、声线身份、合成和自身健康；应用通过客户端调用 |
| 应用内可选模块 | Bilibili、节目、梗库、地球探索、特定产品工具 | 启用时注册路由／工具并加载资源，关闭时不进入默认导入与预检链 |
| 按需外部能力 | 现有 RVC／音频工作服务、mc-mcp；必要时才增加独立 ASR 或 embedding 服务 | 承担独立模型环境、GPU 或外部世界执行 |
| 开发与训练环境 | 测试、浏览器验证、训练、批量数据处理、Electron 打包 | 独立安装规格，不进入主应用运行环境 |

默认安装和启动的目标是**应用 + Redis，连接已准备好的 Qwen 服务及所选 LLM 端点**。RVC、Minecraft、地图与训练工具不参与默认启动。

这能让主应用无需本地 GPU 推理环境。由于用户选择保留 Qwen，本机完整语音部署仍需要其宿主运行环境和模型；首次模型准备、应用部署、应用重启必须分别说明。第一轮继续遵守本机 loopback 约束，跨机器托管属于后续网络与鉴权设计。

“通用服务”指任务契约与业务无关，例如接收音频／文本、返回音频／转写／向量及真实模型身份。服务可以留在同一仓库，但拥有独立环境、锁、构建输入和生命周期。单独仓库、服务发现系统、统一 GPU 大网关均不是本轮必要条件。

### 独立服务的判定

满足以下情况才考虑拆成进程服务：存在主应用不需要的 CUDA／模型环境；依赖版本或解释器冲突；长任务需要独立资源预算、取消和恢复；需要被多个应用复用；更新周期明显不同。

仅做短时业务判断、字符串处理、状态转换的模块，优先留在主应用内，通过清晰接口解耦。多个音频能力可复用现有宿主音频服务边界，避免每个模型新增一个常驻服务。

服务契约至少覆盖任务 ID、模型／声线版本、超时、取消、限流、失败原因和健康状态。只对可安全重试的操作重试，真实结果与降级结果必须可区分。复用 GPU 服务时需要有界队列与资源预算，不能由多个客户端各自反复启动或抢占模型。

健康与就绪也按这套边界表达：进程存活不代表所选能力已可用；`/ready` 聚合已启用且必需的能力，关闭的 RVC 等能力不进入门槛。默认 Qwen 不可用时，应明确报告语音未就绪，整体必需能力验收不能通过，但已可用的文字与后台路径可继续服务。不能为了“快启动”隐藏失败。

## 4. 依赖与功能的取舍

| 模块 | 第一轮处理 | 需要保留的能力／代价 |
| --- | --- | --- |
| LangGraph、Starlette、Socket.IO | 保留；审计周边包的实际用途 | 保留状态图、协议与恢复语义，避免一次全面框架重写 |
| LLM | 默认使用已有 HTTP／兼容接口 Provider；本地 LoRA 与训练放独立环境 | 云端依赖密钥、网络和调用费用；完全离线部署仍要准备独立模型服务 |
| Qwen TTS | 复用现有宿主；主应用仅携带客户端 | 保留真实声线与身份验证；应用重启不重载模型 |
| ASR／VAD | 麦克风启用时才初始化；优先复用已有远端 ASR。按键录音路径可先避免本地神经 VAD | 自动断句与抗噪能力可能有差异，要使用实际录音样本比较；不可把 Mock 当作正式替代 |
| 情绪与口型 | 保留现有结构化标记、规则映射和音量包络；不默认增加独立情绪模型 | 核心表演和播放同步继续验收，效果上限与语音资源相关 |
| 长期记忆 | 保留 v2 的原子、版本、身份、作用域和治理；明确区分 FTS 检索与语义检索模式 | FTS 简化部署，但同义表达和隐含含义召回可能下降；不能宣称与向量检索等价 |
| 向量与 embedding | 关闭时不导入或加载；语义检索确有需要时评估外部 embedding，再决定索引位置 | 增加外部服务会带来网络、隐私和可用性成本；没有测得需要时不新建服务 |
| RVC／分离／唱歌 | 保留现有宿主服务边界，唱歌启用时才准备 | 不进入核心启动门槛；所选真实声线不可静默用原声替代 |
| Minecraft | 保留独立 mc-mcp，通过现有桥接调用 | 主应用默认不安装 Node bot 依赖、不启动游戏服务器 |
| Bilibili／搜索工具 | 应用内模块与可选安装规格；审计 `bilibili-api-python`、`langchain-community` 等闭包 | 启用后原有行为仍需完整验证；不能删除依赖后保留失效入口 |
| Cesium／Electron | Web 核心构建按能力打包，地图和桌面打包工具单独安装 | 运行产物精简与构建环境精简分别测量 |
| 观测 | 保留本地错误、链路与播放证据；外部采集栈按需配置 | 不以去掉真实执行证据换取更小的依赖清单 |

依赖管理继续以 `pyproject.toml`、`uv.lock` 和生成的 requirements 为真相源。适合共存的功能依赖用 extras，开发依赖用 groups；GPU 服务及有版本冲突的环境单独锁定。uv 官方文档说明 workspace 共用锁，冲突依赖或需要独立环境时不宜强行放入同一 workspace。[依赖分类](https://docs.astral.sh/uv/concepts/projects/dependencies/)、[workspace 边界](https://docs.astral.sh/uv/concepts/projects/workspaces/)

保留已有 `test/smoke/selftest/production` 的验证语义，通过有类型的能力配置表达启用范围。能力配置应是安装、注册、初始化和就绪规划共同读取的事实来源；不新增重复的功能开关文件或第二套 Provider 注册器。

## 5. 阶段实施计划

各阶段是独立交付批次，先通过出口条件再推进。工期仅为初步人日估计，阶段 0 后根据实际映射和依赖重新估算。

| 阶段 | 工作与主要位置 | 出口条件 | 估计 |
| --- | --- | --- | --- |
| **0：冻结核心契约与成本基线** | 定义核心场景、能力清单和依赖用途；区分构建、安装、模型准备、应用启动、首轮对话和实际播放。复用现有生命周期与测量工具 | 核心场景清单、逐项依赖归属、原始测量与待核实项齐备；优化目标在修改前冻结 | 0.5–1 天 |
| **1：解除默认生命周期耦合** | 修改生命周期规划，使 Qwen 与 RVC 按启用能力进入计划；连接服务与管理服务的权限分开。应用部署复用健康的 Qwen，不要求唱歌预检 | 无 RVC、mc-mcp、本地 ASR 时核心路径正常；已准备的 Qwen PID／声线身份跨应用重启保持；未启用服务不被探测或启动 | 1–2 天 |
| **2：形成真正的核心安装与按需组装** | 收紧项目依赖、导出脚本、ProviderPool／ServiceContext 组装和路由注册；已有 Provider 工厂按选中配置延迟导入 | 仅安装核心规格即可导入、启动和完成核心场景；可选依赖卸载后核心仍可用；应用环境无 Torch／Transformers／训练库 | 1–2 天 |
| **3：低成本能力模式与推理边界** | 在记忆 v2 内形成显式 FTS／语义模式；语音输入按需初始化；分别锁定现有 Qwen、RVC 环境，补齐通用任务边界 | 记忆持久性、身份隔离和治理不变；检索与语音效果在冻结样本上达到目标；推理故障影响明确，结果不冒充真实成功 | 2–3 天 |
| **4：压缩构建与分发** | 地图关闭时不复制 Cesium；隔离 Electron／评审工具安装；CI 产出可复用镜像，日常优先现有 `anima-deploy` 路径。审计 ffmpeg 等系统包的实际核心用途 | 普通部署不需要本地 Node、pnpm、编译器或训练工具；未启用资源不在产物中；两个正式入口仍通过验收 | 1–2 天 |
| **5：收尾与成本复测** | 清理已确认不用的依赖／过期兼容分支，合并安装与启动文档；以同样条件复测，生成核心／可选能力成本对照 | 所有必要质量组与真实入口验收通过；依赖、体积、启动和维护步骤的改善有原始证据；可恢复上一发布版本 | 0.5–1 天 |

阶段 0 完成后依次推进 1、2；阶段 3 的具体替代项只选择已证实有收益的部分。阶段 4 的构建精简可在安装边界稳定后并行准备。**阶段 1–2 是首个交付里程碑：让不用的功能真正不影响核心安装和启动。** 无需等待所有模型服务重构完成才获得这部分收益。

### 每阶段的验证与回退

| 变化类型 | 必须保住什么 | 回退方式 |
| --- | --- | --- |
| 生命周期／就绪 | 按能力规划、精确进程归属、Qwen 复用、关闭可选能力不触发外部服务 | 切回上一生命周期与能力配置；不停止其他应用拥有的宿主服务 |
| 安装／导入 | 干净核心环境能启动；启用但缺少依赖时给出具体原因；不静默降级成 Mock | 恢复上一锁定依赖与发布镜像 |
| 检索／音频替代 | 相同样本中的质量、延迟和失效行为；实际播放状态及任务关联 | 切回原 Provider／检索模式；保留原始记忆，索引只在隔离副本验证 |
| 发布／资源 | `/live.html`、`/dashboard` 的实际服务和资源指纹，必要的权限与协议 | 部署上一不可变镜像；不得以清空运行数据作为回退 |

源码实施时按 `tooling/quality.yml` 运行对应影响感知验证，不手工跳过规划器要求的检查。浏览器、Docker 和性能测量只在对应阶段使用；本次计划文档不运行这些检查。长 GPU 作业遵守既有进程归属、峰值探针与显存预算规则。

## 6. 度量与完成标准

阶段 0 将安装量、镜像大小、启动和质量分别冻结条件。冷缓存与暖缓存至少各采集 3 个独立样本，记录每阶段耗时、样本数、中位数、范围、原始日志与资源占用；网络拉取、模型冷加载和首轮请求不得并入同一个“启动秒数”。测试机器、版本、资源、已加载模型与配置前后保持一致。

| 指标 | 当前信息 | 目标／判定 |
| --- | --- | --- |
| 默认功能前提 | 启动计划包含 Qwen 与 RVC；模型池初始化多类服务 | RVC／游戏／地图／训练不参与核心启动；关闭能力不安装专属依赖、不导入实现、不初始化或预检；轻量契约可保留 |
| GPU 环境边界 | 主 Dockerfile 已排除 GPU 包 | 保持主应用无需本地 GPU 推理包；宿主服务独立准备和复用 |
| 依赖体积与镜像大小 | 未测；119 条锁定声明仅作清单线索 | 阶段 0 冻结目标；以实际安装／传输体积及构建耗时评价，不以删包数替代 |
| 应用重启 | 未测 | 不重新加载 Qwen，不牵动 RVC；核心就绪耗时在相同条件下改善 |
| 模型冷启动 | 未测 | 单独报告，并尽量从普通应用重启链移出 |
| 核心质量 | 本轮未运行验收 | 角色回复、Live2D、记忆、Qwen 声线与实际播放证据通过；质量替代项达到冻结门槛 |
| 运维负担 | 缺少当前操作步骤实测 | 明确首次准备、部署、重启、添加能力、升级与回退的入口和前提；普通运行者无需安装开发工具 |

精简完成的判断是核心能以明确前提快速部署、可选能力故障隔离、必要效果保留，且这些改善有可复验数据。缩小体积但增加人工步骤，或启动更快却丢失记忆／真实声音，均不算达成。

## 7. 条件性后续：是否移除 Redis

先完成上述里程碑，再决定是否值得压缩到单应用容器。当前 Redis 同时服务于登录和检查点，替换需要一个单独决策：单实例 SQLite 会话是否足够；登录撤销和凭据版本如何处理；检查点、工具审批和重启恢复能否保持；读写并发与备份如何验证。

LangGraph 官方区分检查点与长期存储，并将 SQLite 描述为本地开发用途；因此不能凭“有 SQLite Saver”就宣称它已满足本项目部署与恢复需求。[持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

只有前述成本已经下降、用户仍明确需要单容器形态，且替代通过专项验证时再推进。否则保留一个 Redis，比引入新的自制持久化与会话系统更符合本轮压缩目标。不得用进程内 saver 冒充可恢复执行。
