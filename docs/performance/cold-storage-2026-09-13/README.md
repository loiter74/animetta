# Anima 冷构建优化与 HDD／SSD 对比

HDD 基线、候选与补测已完成，代码优化达到采纳门槛；模型介质对照也已完成，原 SSD 模型路径已恢复。Docker 官方迁移两次因返回码处理问题回滚，实际数据仍在 E 盘，SSD 构建场景阻塞。最终代码验证、正式及开发入口冒烟均已通过；修复后单次正常 Docker 停启通过，但此前临时 socket 故障复发仍构成稳定性限制。以 `407a6487` 的实现作为新基线，旧报告的单次 796.68 秒只作历史参考。耗时预测在无 gcc 探针和正式修改之前冻结；未取得的数据不填写为零或预测值。

## 实验设计

| 对比 | 固定条件 | 样本数 |
| --- | --- | ---: |
| 原实现 HDD → 候选实现 HDD | 物理磁盘、功能配置、基础镜像 digest、BuildKit 版本、依赖锁、测量驱动 | 每侧 3 次 |
| 最终实现 HDD → 同实现 SSD | 源码与上述条件一致，只改变 Docker 数据盘 | 每侧 3 次；符合条件的 HDD 样本复用 |
| Qwen、RVC 模型 SSD → HDD | 解释器、代码、模型内容与身份一致，只切换模型文件位置 | 每种模型、每种介质 3 次 |
| 模型文件无缓冲读取 | 相同文件字节、读取块大小与探针 | 每种介质 3 次 |

代码候选只有完整验收通过且冷构建中位数降低至少 5% 才采纳。SSD 只有冷构建中位数降低至少 20%、三次验收通过、无存储错误、迁移后空间充足，且 Docker Desktop 正常停止／启动后恢复通过，才保留；否则恢复 HDD。两项门槛在本轮采样前由用户批准，不随结果调整。

测量机器为 i5-14600KF（14 核／20 线程）、约 31.78 GiB 内存，Docker 虚拟机配置为 10 CPU／约 10.4 GB。E 盘对应 `WDC WD5000AAKX-60U6AA0` SATA HDD；C、D 盘同属 `J.ZAO 5 SERIES 1TB SSD` NVMe 物理盘，不能将 C 与 D 当作两块独立 SSD。初始 Docker 数据盘为 `E:\DockerDesktop\wsl\disk\docker_data.vhdx`，模型主要在 C／D。空间与 VHDX 大小在迁移前重新测量，不沿用实验开始时的剩余空间。

工具固定为 Docker Desktop 4.81.0、Engine 29.6.1、Compose 5.2.0、BuildKit v0.32.2；硬件、版本、基础镜像 digest 和时间戳见[环境快照](environment.json)。测量驱动没有重启电脑；基线完成时根据系统启动时间与事件日志回查连续性，不能将这一回查写成实验开始前已采集的启动快照。候选样本另有开始状态快照。后续中断期间发生外部重启，模型实验因此单独记录启动批次，不能声称本轮全程未重启。

## 缓存和计时约定

- 严格冷构建指每次独立 builder 的 BuildKit 缓存初始为 0 B；没有清除 Windows、Linux 或设备缓存。基础镜像解析 digest 必须逐次相同，不能仅比较可变 tag。
- 构建使用现有 `scripts/benchmark_startup.py` 的真实后台 receipt 与单调计时。完整就绪、页面验收、构建器准备和迁移成本分别列出；并行步骤或续跑等待不能相加代替墙钟。
- 物理磁盘与 CPU 由 `scripts/measure_storage_telemetry.ps1` 持续采样。间隔为上次采集结束后等待 2 秒，真实间隔以时间戳为准；不是严格 2 Hz 或固定 2 秒。保留原始 idle、读写速率、队列和 CPU 数据，活动率按 `clamp(100-idle, 0, 100)` 派生。
- 模型服务停止后重新启动不代表系统文件缓存为空。首次观察与随后样本分开列出；驱动不重启电脑、不清空系统缓存。中断期间外部重启不算主动受控实验，不能据此宣称已验证跨电脑重启稳定性。
- `scripts/benchmark_storage.py` 使用 Windows `FILE_FLAG_NO_BUFFERING` 和对齐内存读取完整模型文件。它绕过 Windows 文件数据缓存，不清除设备缓存，不能替代模型加载计时。SHA 校验在读取计时前进行，会影响其他使用缓存的读取，必须记录这一限制。实现依据 [Microsoft 无缓冲 I/O 文档](https://learn.microsoft.com/en-us/windows/win32/fileio/file-buffering)。

## 复现入口

在仓库根目录使用 Python 3.13。应用启动与构建继续使用现有生命周期和基准驱动，存储辅助不改变正式启动接口。

```powershell
py -3.13 scripts/benchmark_storage.py --file <模型文件> --file <辅助模型文件> --samples 3 --output <本轮输出.json>
powershell -NoProfile -File scripts/measure_storage_telemetry.ps1 -OutputPath <遥测.jsonl> -StopPath <停止标记文件>
```

模型读取探针只接受完整普通文件，拒绝重复输入，短读、文件变化或 I/O 失败会终止采样并留下失败记录。输出必须是新文件，不覆盖已有证据或模型。遥测使用每轮独立的输出与停止标记路径，由测量包装器隐藏启动、在 finally 中写入停止标记并等待退出。不要在构建或模型计时期间并行执行此读取探针、测试、依赖安装或文件复制。

每次冷构建使用以下顺序，替换唯一 builder、Compose 项目和输出目录。先通过规范生命周期停止占用正式端口的应用，保留宿主模型；加载现有环境配置及同一代理配置。`create`／`bootstrap` 不属于构建计时，必须保存 `du` 的 **0 B** 证据后才测量，且不切换用户默认 builder。

```powershell
docker buildx create --name <唯一builder> --driver docker-container --driver-opt default-load=true --driver-opt image=moby/buildkit@sha256:28a898719c18a33f4e8000685287fa36fd0dd9560c6440227d3a732d79bb41d8 --driver-opt env.HTTP_PROXY=http://http.docker.internal:3128 --driver-opt env.HTTPS_PROXY=http://http.docker.internal:3128 --driver-opt env.NO_PROXY=localhost desktop-linux
docker buildx inspect --bootstrap <唯一builder>
docker buildx du --builder <唯一builder>
py -3.13 scripts/benchmark_startup.py measure --root . --env-file .env --phase <before或after> --scenario cold-build --samples 1 --project <唯一项目> --builder <唯一builder> --http-port 80 --backend-port 12394 --output <新输出目录>
```

测量前开始遥测，驱动退出后停止遥测并等待子进程退出。结束后设置该样本的 `COMPOSE_PROJECT_NAME` 和 `ANIMETTA_IMAGE=animetta:<唯一项目>`，调用 `runtime_lifecycle.py anima-down --wait`，再执行 `docker buildx stop <唯一builder>`；保留构建缓存，不执行 prune。正式实例最后统一恢复。完整调用参数及起止时间保存在原始 receipt；基础镜像 digest 必须与环境快照核对，不一致则不能纳入同条件比较。

## 独立依赖探针

全新 0 B builder 中去掉 gcc 后，现有锁定依赖完整安装并通过依赖检查，共 116 个分发包。`qrcode-terminal 0.8` 和 `jieba 0.42.1` 仍从源码打包，未强制全部使用预编译 wheel。新虚拟环境随后置于基线的实际 runtime 系统库环境，断网导入 21 个关键模块成功；导入位置均来自新虚拟环境，`gcc`／`cc` 均不存在。

这项探针的构建耗时 136.630 秒只用于确认依赖兼容性，不能与完整应用冷构建比较。候选实现仅删除 gcc 安装段，保留运行库及功能预热。删除后只有一段 apt，因此不再进行两段 apt 缓存拆分实验；保留原有 `sharing=locked`。实际代码收益由随后的三次完整候选测量决定。

## 候选测量中的失败与补测

候选 c3 的镜像构建成功，耗时 **747.087 秒**，完整就绪与服务日志检查通过；随后冻结浏览器驱动访问 Dashboard 等待 `DOMContentLoaded` 超时，整轮验收失败。c3 不计入完整成功样本，也不从原始数据或构建时间中删除。

同实例的 HTTP 检查正常，浏览器重放也曾再次超时。请求跟踪将阻塞范围缩小到某份 CSS 请求发往 nginx 之前：失败窗口 nginx 未收到该请求，其他页面资源正常，直接读取该 CSS 返回 200。增加路由跟踪后的诊断通过，随后原封不动的冻结驱动也通过；镜像与实例未改变。**准确的浏览器内部原因未证实，不能宣称已修复。** 诊断成功不会覆盖原样本失败。

因此补一个独立空缓存 c4，并同时报告原始 c1–c3 构建中位数、全部构建 receipt 和完整成功集合。只有原始三轮与三次完整成功集合都满足 5% 门槛才考虑采纳，避免因排除失败样本而制造收益。补测、诊断等待和最初 builder 准备超时均另列为实验成本，冻结预测保持原样。

完整成功集合 c1／c2／c4 的中位数为 **719.820 秒**，最小／最大 **713.186／733.882 秒**。相对基线节省 **80.340 秒／10.04%**，加速比 **1.112×**。原计划 c1–c3 的构建中位数同为 719.820 秒；四次成功构建 receipt 全部纳入时，中位数为 **726.851 秒**，改善 **9.16%**。完整成功率为 **3/4**，不是三轮全部通过。

保留删除 gcc 的候选：三次完整功能验收通过，原三轮与完整成功集合均达到预定 5% 门槛。四个候选镜像的实际构建输入指纹相同，为 `52bc643ab11e296685d74bb4eabd833f05831cf1f7ee78420d19bd2e693c7979`；基线与候选的 216 个 runtime APT 包版本逐项一致。工作区全量摘要会随报告更新而变化，不能代替镜像输入指纹。

719.820 秒位于冻结的 650–780 秒区间内，比区间中点 715 秒高 **4.820 秒／0.67%**；区间外偏差为零。此次收益主要来自删除 gcc 安装分支及其串行等待，Python 安装能够与运行库安装并行。runtime apt 本身没有提速，候选仍耗时约 517–553 秒，不能把该阶段宣称为已优化。

APT 日志显示候选 runtime 包下载均约 135 MB、71–72 秒；从首次解包到 RUN 结束仍约 424–460 秒，包含解包、配置和收尾，不等同于纯磁盘时间。基线 gcc 首条输出之前有很长等待，但日志没有直接的锁获取事件，只能将首输出时间当作前置等待上界。原始阶段记录保留 `Fetched` 文本及首解包／配置时间，缺失字段不填估计实测值。

## 模型实验基线与冻结预测

早期先导使用的驱动在规范 stop 返回后立即断言进程消失，RVC 第二轮前遇到旧进程短暂残留而终止；没有启动第二轮。修订仅在**启动计时之外**增加最多 10 秒的精确 PID／创建时间和模块树退出等待，超时仍失败，并将实际额外等待单列。旧 Qwen 三轮和 RVC 首轮先导保留，正式 SSD 基线使用修订驱动重测。修订后的正式样本不能冒充重启后首次观察。

### 官方迁移失败：SSD 构建缺测

通过正常设置页面选择 `C:\DockerDesktop\wsl` 后，Docker 自行追加 `DockerDesktopWSL` 子目录，并执行自身的 Robocopy 迁移。两次复制阶段分别耗时 **290.305 秒**和 **300.665 秒**，最终均记录 `exit status 1`、`New setting not applied`，实际设置回滚 E 盘。第二次触发来源不确定，记录为未确认的外部输入或异步操作，不能归因于用户；不进行第三次重复迁移。

[微软文档](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/robocopy)定义返回码 1 为复制成功，本机签名与日志支持 Docker 将成功码误判为失败的判断；[同版本公开问题](https://github.com/docker/desktop-feedback/issues/533)也报告了相同现象。目标留下非活动副本，但文件存在不代表实例使用 SSD。镜像与卷身份核对保留，未手改设置、移动 VHDX、重置 Docker 或安装新版本绕过本轮固定版本契约。

因此 SSD 三次冷构建为**缺测／阻塞**，不能计算磁盘收益、组合收益或 SSD 预测误差，也不能判定 SSD 保留条件通过。原预测 200–500 秒保持原样。原数据仍在 E，离线备份和失败迁移副本均保留，等待后续受支持的迁移修复；副本占用空间单列，不作为在用 SSD 布局。
