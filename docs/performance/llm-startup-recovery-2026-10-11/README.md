# LLM 启动瞬时故障恢复验收

本轮解决启动阶段的 LLM 探测超时：保留真实供应商、配置模型和严格就绪检查，在原服务进程中退避重试。正常启动中位数从 **16.49 秒变为 16.94 秒**；两次受控故障在超时后分别 **3.70 秒、3.65 秒**恢复真实就绪，恢复过程中容器与后端 PID 均未变化。角色对话、Live2D、现有 Qwen 实际播放和短期对话连续性通过验收，最终恢复正常镜像与运行配置。

## 根因与实现

[上一轮启动报告](../startup-speed-2026-10-11/README.md)保留了 `ss-base02`、`ss-base04` 的真实失败记录。五秒 LLM 探测预算超时后，失败结果和已经完成的探测任务被保留，后续没有新探测机会；完整 `/ready` 持续 503，生命周期等待最终到期。原故障具体发生在哪个 LLM 子请求仍无法确定。分词器的已捕获 TLS 错误与这条永久未就绪路径分别处理，不能混为同一根因。

- `session_context.py` 复用当前探测任务；仅在任务结束且失败原因可恢复时创建下一次探测。成功与固定错误仍保留原结果。
- `provider_pool.py` 在现有初始化任务中按 **1、2、4、8、16、30、30…秒**退避，复用共享引擎。关闭时沿用现有取消和资源清理路径。
- `readiness.py` 共用一份瞬时失败原因定义：`timeout`、`connection_error`、`rate_limited`、`provider_unavailable`。401、403、缺少凭据、缺少模型等错误阻止就绪。
- 保留原来的单次五秒总预算、真实模型目录请求及配置模型别名请求。HTTP 就绪处理器只读缓存结果；健康首检成功时没有新增请求或等待。

未新增产品配置开关、后台常驻服务或安装依赖。LangGraph 编排、记忆路径、模型、声线及宿主 Qwen 生命周期沿用现有实现。

## 冻结条件与预测

修复前源码为 `43cbfe293a548d65c4b0018e226bc1fbe810730c`。两组均使用 production、端口 80/12394、相同三个命名持久卷、同一私有凭据和驻留 Qwen；计时前完成一次新镜像构建与预热。普通计时阶段没有并行构建、安装、质量门禁、浏览器或故障注入。

[预测](evidence/prediction.json)在实现前冻结：每组两个样本、健康启动中位数不超过 18 秒、注入超时后 60 秒内在同一进程恢复。[测量契约](evidence/contract.json)与原预测字节保留。故障载体在执行前通过[独立修订](evidence/prediction-amendment.json)改为正常镜像上的只读启动脚本挂载：镜像构建指纹保持真实，故障运行时指纹独立。

## 正常启动复测

主要指标是实际 `animetta-start` 步骤开始到 `animetta-ready` 就绪反馈，包含 Compose 启动及实际就绪等待；不是纯 Python 初始化耗时。CLI 指标从请求到命令完成，容器指标从实际 `StartedAt` 到就绪反馈。

| 组 / run ID | 启动步骤→就绪（秒） | CLI（秒） | 容器→就绪（秒） |
| --- | ---: | ---: | ---: |
| 基线 `llmr-base01` | 16.535257 | 25.589977 | 7.996898 |
| 基线 `llmr-base02` | 16.442382 | 23.694489 | 8.016070 |
| 修复 `llmr-after01` | 17.074453 | 25.813704 | 8.739906 |
| 修复 `llmr-after02` | 16.809628 | 25.504077 | 8.587093 |

主要指标中位数：**16.488820 → 16.942041 秒，增加 0.453221 秒（2.75%）**。基线范围 16.442382–16.535257 秒，修复范围 16.809628–17.074453 秒。满足原 18 秒预测；本轮没有测得启动加速，收益在于故障恢复。每组只有两个样本，真实 LLM 网络延迟未受控，不能据此估计 p95、稳定失败率或把差异完全归因于代码。保留镜像与模型缓存，本轮不是首次安装下载基准。

原始记录见[基线汇总](evidence/baseline-summary.json)、[完整阶段账本](evidence/after.json)以及 `evidence/raw/`、`evidence/after/`；构建预热、故障尝试和最终恢复没有计入普通启动样本。

## 真实故障恢复

测试启动脚本仅延迟第一次发往 `api.deepseek.com` 的异步 HTTP 发送十秒，随后全部请求委托原生 HTTP 传输；原五秒总预算取消该请求。未替换供应商或模型响应，TLS、凭据和真实就绪判断保持原样。故障镜像内容与正常镜像相同，附加只读挂载由独立运行时指纹标识。

| 尝试 | 实际恢复证据 | 超时取消→真实就绪 | 后端 PID |
| --- | --- | ---: | ---: |
| `llmr-fault01` | 原 ASGI 日志 17 次 `/ready` 503 后转为 200；真实目录及配置模型请求均 200 | 3.697402 秒 | 22，前后相同 |
| `llmr-fault02` | 修正观测脚本后直接采集真实未就绪→就绪及组件状态 | 3.648009 秒 | 23，前后相同 |

每次尝试各自的容器 ID、`StartedAt` 和后端 PID 保持一致，`RestartCount=0`。第一轮延迟在 4.955033 秒被原总预算取消，约一秒后开始真实重试；真实目录与配置模型请求依次通过后才就绪。见[第一轮恢复证据](evidence/fault01-recovered-observation.json)、[第二轮观测](evidence/fault02-observation.json)及各自原始日志。

第一轮独立观测器遗漏 `RemoteDisconnected`，提前退出。原[失败观测](evidence/fault-observation.json)及[原日志](evidence/failed-first/fault01-app.stdout.log)均保留；503 的响应正文没有保存，状态与时间从原 ASGI 访问日志恢复，严格最终响应另有实际记录。采集脚本补充 `ConnectionError` 处理并记录安全异常类型；原[恢复决定](evidence/retest-decision.json)保留，后来已启动的独立补测按[执行记录](evidence/fault02-execution-receipt.json)完成。共两次故障尝试，没有追加或替换普通速度样本，也没有重演已通过的角色验收。

持续上游故障时保持未就绪并继续有界频率的重试；生命周期 CLI 的等待截止时间仍保留。本轮实测受控单次延迟恢复，不代表对所有网络故障或长期不可用情况的全面可靠性评估。

## 核心能力与正常配置恢复

[真实角色验收](evidence/acceptance/llmr-fault-role01.json)在恢复后的原实例通过：

- 角色对话走真实 Socket.IO 与配置 LLM，首回复 2.769 秒。
- 现有 Qwen 生成音频，`HTMLMediaElement` 实际 WAV/blob 播放完成且音频非零；首音频 7.870 秒，持久播放状态为 completed、计数为 1，任务 `877334cf-8046-41c4-83d5-d43539cc069c`。
- Live2D 实际模型加载成功，真实音频任务对应 232 次嘴型应用。
- 普通事实写入与不含答案的追问，在同一 Socket 与逻辑会话中正确回忆，两轮连续性通过。本项覆盖短期连续性；原 `long_term_memory_mode=off` 设置保持，未据此声称验收长期记忆质量。

最终通过规范生命周期恢复正常镜像 `animetta:llm-startup-recovery-normal-20261011`，构建指纹为 `0db686508c7aca6d417b6430d07c2942a357b5bb334e879ef6533528d2af5d2b`；[最终恢复结果](evidence/after/llmr-restore01-result.json)、[实际快照](evidence/after/llmr-restore01-sample.json)和[终态身份及就绪证明](evidence/final-identity-ready.json)保留。故障注入挂载移除，宿主 Qwen 沿用原服务，PID 14240/16104 保持。
