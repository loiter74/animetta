# 长时间运行内存保留修复与首音频基线

日期：2026-10-14（北京时间）。先修复三处保留边界，再更新正式实例并完成三次真实首音频测量。

## 结果与范围

- 会话正文窗口保持 6 轮；本地提交去重保存最近 1,024 个已完成任务，按提交顺序淘汰。窗口内重复提交仍被拒绝。超过该窗口的旧 ID 不再由本地集合保证去重，入口 Command Inbox 的七天结果重放、冲突与未知副作用处理保持原规则。
- 回复排队与处理耗时各保留最近 1,024 条，列表/JSON 形状不变；累计成功、失败和丢弃计数继续累计。
- 聊天锁使用弱引用注册；运行者和等待者持有强引用，最后一个使用者退出后释放登记。保留同会话串行、取消等待者不破坏锁的行为。
- 三处结构的隔离保留分配在 3 万轮时由中位 10,193,636 B 降为 217,296 B（约 9.72 MiB → 0.21 MiB，下降 97.87%）。不是整个服务的 RSS 或多小时直播内存曲线。
- 正式 `/live.html` 的短回复首实际播放中位 2.128 s，范围 1.980–2.472 s，n=3。Qwen 保持加载；这是一份新基线，没有语音提速的前后对照结论。

## 修改前冻结的条件

[原始预测与预算](contract.json) 在产品改动前冻结。相同 [保留探针源码](retention_probe.py.txt) 在修改前后各运行 1,000、10,000、30,000 轮，每个规模三个独立新对象样本；真实调用 commit、聊天锁包装和 ReplyWorker，仅替换领域处理回调为无副作用操作。tracemalloc 在依赖导入后开启，收集前执行 GC。Python 3.13.14 / Windows；不调用真实模型或持久数据。

预期：去重与两组样本各上限 1,024，闲置锁为零，六轮窗口、近期重复拒绝和累计成功计数保留。没有为整个服务 RSS 或 CPU 提速设预测。实际测得探针 CPU 时间略增加，不能声称运行速度改善。
